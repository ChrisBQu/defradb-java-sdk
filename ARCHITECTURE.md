# Architecture

The DefraDB Java SDK embeds a DefraDB node in the host process. Calls cross two native boundaries before reaching DefraDB:

```text
Java application
    │  source.defra API
    ▼
Java SDK
    │  JNI
    ▼
libnativewrapper
    │  C API
    ▼
libdefradb
    │  cgo
    ▼
DefraDB
```

## Components

- `src/main/java/source/defra` contains the public Java API and native method declarations. `DefraNode` owns the native node handle and is the primary entry point.
- `src/main/c/nativewrapper.c` adapts JNI calls and Java objects to the C API generated by DefraDB.
- `libnativewrapper` is compiled by `src/main/c/build.sh` for Linux or each supported Android ABI.
- `libdefradb` and its headers are produced from the companion [DefraDB repository](https://github.com/sourcenetwork/defradb/tree/develop/cbindings).
- `build-linux.gradle` packages Java classes, runtime dependencies, and Linux shared libraries into a JAR.
- `build-android.gradle` packages Java classes and per-ABI shared libraries into an AAR.

## Runtime lifecycle

Constructing `DefraNode` creates an embedded native node and retains its native handle. The node also owns a background dispatcher for subscription callbacks. Calling `DefraNode.close()` stops that dispatcher and releases the native node, so applications must close every node they create.

Native libraries are loaded from the packaged artifact by `NativeLoader`. Linux builds locate the paired shared objects beside one another through an `$ORIGIN` runtime search path; Android selects libraries from the device ABI directory in the AAR.

## Source compatibility

The JNI wrapper is compiled against headers generated by a particular DefraDB checkout. Changes to DefraDB's C bindings may require corresponding Java and JNI changes, so build and test the SDK against the DefraDB revision that the application will use.
